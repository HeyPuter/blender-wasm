# blender-wasm — Blender + EEVEE rendering via WebGPU in WebAssembly

Cross-compiles **Blender** to WebAssembly (Emscripten) with a **WebGPU GPU backend**,
so EEVEE can render in the browser (or in Node via Dawn). WebGPU is required because
EEVEE-Next is compute-shader based, which WebGL2 cannot do.

The pipeline is: Blender GLSL → SPIR-V (shaderc) → WGSL (Tint) → `WGPUShaderModule`
→ render/compute pipelines, all running inside the wasm module against a real
WebGPU device handed in from JS.

---

## Layout

| Path | Tracked? | What |
|------|----------|------|
| `Makefile` | ✅ | build orchestration (see targets below) |
| `scripts/` | ✅ | build + link + verify scripts (`link_blender_web.sh`, `link_blender_node.sh`, `build_*.sh`, `*.mjs` harnesses) |
| `cmake/` | ✅ | Blender wasm CMake cache + compat shims |
| `smoke/` | ✅ | standalone WebGPU/pthreads probes (`wgpu_triangle.c`, `wgsl_probe.cc`, …) |
| `web/` | mixed | `*.html` / `*.mjs` harness pages tracked; built `blender.{js,wasm,data}` ignored |
| `node-webgpu/` | mixed | `*.cjs` Node harnesses tracked; built `blender_node.*` ignored |
| `emsdk/ deps/ wasm-sysroot/ build-blender/ build-cycles/ blender/ node_modules/` | ❌ | all regenerated by `make` |

The WebGPU backend and all WASM source patches live in the **fork itself**
(`blender/source/blender/gpu/webgpu/` + the wasm32 build fixes), committed there
and pulled by `make blender` — there is no separate patch step or snapshot.

## Prerequisites

- Linux, ~20 GB disk (toolchain + deps + build trees are large).
- `cmake`, `ninja`, `python3`, `git`, `git-lfs`, `pkg-config`, a host C/C++ compiler.
- `node` ≥ 18 (for the Playwright/Node harnesses).
- For the Node + lavapipe path: `mesa-vulkan-drivers` (provides lavapipe,
  `/usr/share/vulkan/icd.d/lvp_icd.json`).
- No GPU required — software WebGPU is used (see two paths below).

## Build

The Makefile chains everything. From scratch:

```bash
make toolchain          # fetch + activate Emscripten SDK (emsdk/)
make blender            # clone the pinned Blender fork (blender/)  — see LFS note
make blender-assets     # pull LFS datafiles (fonts/icons/startup.blend)
make deps               # cross-compile dependency stack (deps/, wasm-sysroot/)
make configure-blender  # CMake configure → build-blender/ (also builds native codegen tools)

# Build the wasm module (produces build-blender/bin/blender.{js,wasm}):
ninja -C build-blender blender
```

Then link for one of the two runtimes below.

> **Incremental backend work:** after editing `blender/source/blender/gpu/webgpu/*`,
> rebuild just the GPU lib with `ninja -C build-blender lib/libbf_gpu.a`, then relink
> (`scripts/link_blender_web.sh` or `scripts/link_blender_node.sh`).

## Run path A — Browser (chromium + SwiftShader)

Relinks the wasm for the web (WASMFS, asset preload, device handed in from JS),
emitting `web/blender.{js,wasm,data}`, then drives it in headless chromium.

```bash
make blender-web              # → scripts/link_blender_web.sh → web/blender.{js,wasm,data}
make verify-blender-webgpu    # → scripts/verify_blender_webgpu.mjs (real WebGPU device in Blender)
# pixel capture of a render:
node scripts/capture_eevee.mjs
```

**Limitation:** chromium's headless WebGPU uses **SwiftShader**, which only exposes
WebGPU *baseline* limits (`maxStorageTexturesPerShaderStage=4`,
`maxComputeWorkgroupSize=256`). EEVEE-Next's compute passes exceed these, so the full
lit image can't assemble here — graphics passes (world/background, clears) work,
compute-heavy passes don't. Chrome **cannot** be pointed at lavapipe (it rejects
software/CPU Vulkan devices for WebGPU; tested extensively).

## Run path B — Node + Dawn + lavapipe (real limits, no GPU needed)

Dawn-native (via the `@kmamal/gpu` npm package) backed by **lavapipe** exposes the
device's *real* limits (`8` storage textures / `1024` workgroup) — enough for EEVEE's
compute passes. This is the path to a full EEVEE render on a GPU-less box.

```bash
cd node-webgpu && npm install @kmamal/gpu && cd ..   # one-time
bash scripts/link_blender_node.sh                    # → node-webgpu/blender_node.{js,wasm,data}
cd node-webgpu
VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json node run_blender.cjs
```

Node-build specifics (already baked into `link_blender_node.sh` / `run_blender.cjs`):
`-sMODULARIZE=1`, default **MEMFS** (not WASMFS), `thisProgram:"/blender"` (so Blender
finds `/5.3/scripts`), a polyfilled `navigator.gpu`/`navigator.userAgent`, and
`requestDevice({requiredLimits})` to actually get the high limits.

**Status:** lavapipe lifts the limits and Blender's EEVEE render runs to completion
under Node, but a cross-thread device-handoff issue remains (the device lives on
node-main while the render runs on a worker under `PROXY_TO_PTHREAD`). The candidate
fix is `-sASYNCIFY` so the render stays on node-main and yields at GPU sync points.

## LFS gotcha (push asks for upstream creds)

`blender/`'s `lfs.url` points at **upstream** `projects.blender.org` (so we can *pull*
the datafiles your fork doesn't store). On `git push`, the `pre-push` hook runs
`git lfs pre-push` and authenticates there. You have nothing to upload, so skip it:

```bash
git push --no-verify          # one-off: skip the LFS pre-push hook
# or permanently (only disables LFS *upload*; pull still works):
rm blender/.git/hooks/pre-push
```
